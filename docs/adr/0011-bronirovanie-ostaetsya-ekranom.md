# 0011. Бронирование остаётся отдельным экраном, а не шторкой

**Статус:** Принято (issue #285)

## Контекст

Макет «Focus» (`design_handoff_mahalla_focus/README.md`, 1c) показывает
бронирование как `ModalBottomSheet` поверх карточки места: скрим, лист r28
сверху, ряд дней, сетка слотов, «Отмена» и «Подтвердить · 10:30». PR #283
перерисовал содержимое `BookingScreen` под этот макет — сетка слотов 4×N
(`SLOT_COLUMNS`), время в подписи кнопки подтверждения, — но тип назначения
не менял: это по-прежнему отдельный полноэкранный `composable<BookingRoute>`
в `MahallaNavHost.kt`, а не шторка.

`BookingViewModel` читает `placeId`/`placeName`/`serviceId` и параметры
переноса записи (`rescheduleId` и т. д.) из маршрута через
`savedStateHandle.toRoute<BookingRoute>()`. Экран открывается из двух мест:
с карточки места (`PlaceDetailsScreen`, обычная запись) и из «Моих
активностей» (`MyAppointmentsScreen`, перенос уже существующей записи,
`isReschedule`).

Рассматривали два пути превратить это в шторку:

1. **`navigation-material`** — назначение-шторка в графе Compose Navigation.
   У `androidx.navigation` такого типа нет; единственная реализация —
   архивный, не поддерживаемый `accompanist-navigation-material`
   (последний релиз — под Compose Navigation 2.4, в проекте `navigation-compose
   2.8.5`). Библиотеки в зависимостях нет и никогда не было.
2. **Подъём состояния бронирования в `PlaceDetailsScreen`** — шторка как
   локальное UI-состояние экрана, тем же приёмом, что уже есть в проекте:
   `ReviewFormSheet` и `PaymentConfirmSheet` (`MahallaBottomSheet` в
   `core/ui/components/Sheets.kt`) — обе показываются поверх экрана, который
   их вызвал, без отдельного маршрута.

Оба пути не проходят по одной и той же причине — назначение экрана шире, чем
карточка места. Перенос записи открывает тот же `BookingScreen` из «Моих
активностей», где карточки места нет вовсе: `MyAppointmentsScreen` рисует
только карточки записей (услуга, статус, дата/время, цена) и не запрашивает
данные места. Шторке в варианте 2 буквально нечем стать «поверх» — она либо
получает собственную мини-шапку и превращается в тот же полноэкранный
диалог, только в форме листа, либо перенос записи остаётся отдельным путём
с другим UI, что расходится с текущим устройством `BookingScreen` (один
компонент на обе формы, различие только в заголовке и блоке
`RescheduledServiceBlock`).

## Решение

**Оставляем `BookingScreen` полноэкранным назначением графа.** Расхождение с
макетом 1c — по типу контейнера (экран vs шторка), а не по содержимому:
сетка слотов 4×N и подпись кнопки с временем уже сделаны по макету в PR #283.
Реализовывать шторку не будем ни через `navigation-material`, ни через подъём
состояния.

## Почему не иначе

- **`navigation-material` архивен.** Google перестал его развивать до того,
  как Compose Navigation дошла до типобезопасных маршрутов (`toRoute()`),
  которыми уже пользуется весь граф приложения (`MapPickerRoute`, `OtpRoute`,
  сам `BookingRoute`). Тащить неподдерживаемую зависимость ради одного
  экрана — держать в проекте единственную точку, которую нечем будет
  обновить при следующем апгрейде `navigation-compose`.
- **Подъём состояния ломает перенос записи**, а не просто усложняет его: в
  `MyAppointmentsScreen` нет карточки места, которую шторка могла бы
  перекрыть, и нет вызывающего экрана с состоянием, куда естественно поднять
  форму бронирования. Пришлось бы либо тянуть данные места в «Мои
  активности» ради одной шторки, либо заводить для переноса записи второй,
  отдельный UI — оба варианта дороже, чем экран, который уже работает для
  обоих случаев.
- **Единственный существующий в проекте паттерн шторки** (`ReviewFormSheet`,
  `PaymentConfirmSheet`) — это всегда локальное состояние экрана, который её
  показывает, а не назначение графа. Ни то ни другое расширение не подходит
  под этот паттерн без ломки его смысла.

## Последствия

- Issue #285 закрывается без изменения кода — расхождение с макетом по типу
  контейнера считается осознанным, зафиксировано этим ADR.
- Если в будущем понадобится именно шторка (например, единый визуальный язык
  для всех форм), решать придётся вместе с переносом записи: либо тянуть
  карточку места в «Мои активности», либо проектировать второй UI для
  переноса — в объём этой задачи не входит.
- `docs/UI-INVENTORY.md` обновлён: #285 больше не в списке открытых
  расхождений с макетом.
