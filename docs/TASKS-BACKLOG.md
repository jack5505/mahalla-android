## T1. Картинки: Coil + MahallaAsyncImage (фото мест, блюд, отзывов, аватаров)

*Метки: `ai-task`, `android`*

### Проблема

В проекте **нет загрузчика изображений вообще** — `grep -i 'coil\|glide' gradle/libs.versions.toml` пусто. Вместо фото везде серые скелетоны: `PlaceDetailsScreen.kt:202` рисует `Gallery(photoCount)`, то есть считает картинки и показывает вместо них пустые прямоугольники.

При этом **данные уже приезжают и выбрасываются**: `CatalogApi.kt:51-52` разбирает `logoUrl` и `coverUrl`, `PlaceMappers.kt:95` складывает их в `PlaceDetails.photos` — и дальше от них остаётся только `.size`.

Это главная причина, по которой приложение выглядит пустым (см. `docs/UI-INVENTORY.md` §1). Самая дешёвая задача с самым большим визуальным эффектом — делать первой.

### Что сделать

- Добавить `io.coil-kt:coil-compose` в version catalog (версию подобрать под Compose BOM проекта).
- Компонент кита `core/ui/components/MahallaAsyncImage`: скелетон во время загрузки → фото → фоллбэк-иконка при ошибке/пустом URL, `crossfade`, `contentScale`, `contentDescription` обязательным параметром (в проекте `warningsAsErrors` у lint, см. #39).
- Подключить: `PlaceCard`, галерея `PlaceDetailsScreen`, позиции меню, аватар и фото в отзывах.
- Проверить, что Coil переиспользует OkHttp-клиент приложения **осторожно**: основной клиент несёт `AuthInterceptor`, `GeoHeaderInterceptor` и пиннинг — картинки с CDN не должны получать `Bearer`-токен. Скорее всего нужен отдельный клиент.
- Правила ProGuard для Coil (пригодятся, когда включим R8).

### Готово, когда

На главной и в карточке места видны настоящие фото, битый URL не роняет экран и показывает фоллбэк; `testDebugUnitTest`, `lintDebug`, `assembleDebug`, `assembleRelease` зелёные.

## T2. Профиль: живой профиль, кнопка «Выйти», мои устройства

*Метки: `ai-task`, `android`, `screen`*

### Проблема

**Из приложения нельзя выйти.** `AuthRepository.logout()` объявлен (`AuthRepository.kt:97`) и реализован (`:410`), но из UI не вызывается нигде — единственный вызов во всём `src/main` это `PinViewModel.kt:260`, то есть автоматический сброс после исчерпания попыток PIN. Кнопки «Выйти» на экране профиля нет.

Сам `ProfileScreen.kt` — это язык, тема, адрес сервера и Chucker. Нет имени, номера, аватара, хотя `user` (имя, телефон, аватар) приезжает в ответе `verify-otp`/`pin-login` и уже разбирается.

### Что сделать

- Шапка профиля: имя, номер, аватар (`MahallaAsyncImage` из задачи про Coil).
- **Кнопка «Выйти»** с подтверждением: `logout()` → чистка сессии и PIN → возврат в онбординг через `popUpTo(MainGraph) { inclusive = true }` (`AuthRestartRequired` уже есть в навигации).
- «Мои устройства»: `GET auth/sessions` (`deviceName`, `platform`, `lastActivityAt`, `lastIp`, `trustedDevice`), `POST auth/sessions/revoke`, `POST auth/sessions/{id}/trust`. Текущее устройство пометить и не давать отозвать вслепую.
- Смена PIN — `PUT pin/change`, переключатель биометрии — `PUT pin/biometric` (контроллер `pin-code` бэкендом отдаётся, приложением не используется).
- Учесть: у бэкенда **нет `GET /users/me`** — данные профиля есть только из ответа на вход, значит их надо сохранять локально при входе. Обновление профиля (имя/аватар) до появления эндпоинта не делать.

Слайс эпика #14 — задачу привязать к нему, а не создавать конкурирующий эпик.

### Готово, когда

Из профиля видно, кто вошёл, и можно выйти; список устройств читается и отзывается; тесты ViewModel на выход и отзыв сессии зелёные.

## T3. Кошелёк: настоящий баланс и история вместо зашитого числа

*Метки: `ai-task`, `android`, `screen`*

### Проблема

`feature/wallet/ui/WalletScreen.kt` — 32 строки, из них главная:

```kotlin
private const val DEMO_BALANCE_SUM = 1_284_500L
```

Таб «Кошелёк» **показывает выдуманные 1 284 500 сум каждому пользователю**. Это хуже пустого экрана: пустой экран честен, а этот врёт про деньги. Комментарий в коде («демонстрация форматирования сумм») объясняет, откуда взялось, но пользователь его не читает.

Бэкенд кошелёк отдаёт, приложение о нём не знает.

### Что сделать

- `GET wallet` → `balance`, `bonusBalance`, `heldAmount`, `availableBalance`, `currency`, `status`. Показать доступный баланс отдельно от удержанного — иначе человек не поймёт, почему оплата не проходит.
- `GET wallet/transactions?page&size` → список с `type`/`direction`/`amount`/`balanceAfter`/`createdAt`, группировка по дням, пагинация.
- `POST wallet/top-up` (`amount`, `provider`) — пополнение. Реальный редирект в Click/Payme — отдельная задача, здесь достаточно довести до ответа бэкенда.
- Убрать `DEMO_BALANCE_SUM`. Состояния Loading/Empty/Error через `ScreenStateHost` (кит эпика 2), суммы — `MoneyFormatter` + `TabularNums` (это в текущем экране уже правильно сделано, сохранить).
- Заменить `WalletRepository.walletBalance()` из вертикали еды: он ходит в несуществующий `GET wallet/balance` (правильный путь — `GET wallet`).

Слайс эпика #12.

### Готово, когда

Баланс и история приходят с бэкенда, выдуманного числа в коде нет, `testDebugUnitTest` зелёный.

## T4. Вертикаль «Еда»: переписать FoodApi под реальный контракт бэкенда

*Метки: `ai-task`, `android`, `blocked`*

### Проблема

`feature/food/data/FoodApi.kt` написан по здравому смыслу (эпик 5 — дизайн-репо было недоступно). На живом бэкенде **не работает ни один из шести вызовов**:

| В приложении | На бэкенде |
|---|---|
| `GET places/{id}/menu` | `GET food/places/{placeId}/menu` |
| `POST orders` | `POST food/orders` |
| `GET orders/{id}` | **нет** — есть только `GET food/orders/my` (страница) |
| `POST orders/{id}/cancel` | **нет** |
| `POST places/{id}/promo` | **нет** — промокод это `GET promotions/check` |
| `GET wallet/balance` | `GET wallet` |

Плюс ответы приходят в конверте `{success, data, error}` (`data/network/ApiResponse.kt`), а `FoodApi` ждёт голый JSON — ровно та правка, что уже сделана для каталога в #53.

Отдельно: `PlaceOrderRequest` бэкенда = `placeId, items[{itemId, quantity}], fulfillment, paymentMethod, deliveryAddress`. **Ни модификаторов, ни промокода, ни времени доставки, ни комментария** — то есть шторку модификаторов и слоты доставки из эпика 5 сейчас физически нечем отправить. `ItemResponse` модификаторов тоже не содержит.

Это единственная полностью написанная вертикаль приложения, и на живом сервере она мертва.

### Что сделать

1. **Сначала снять реальные тела curl'ами** по `https://189-74-96-232.nip.io/v3/api-docs`: схемы springdoc перекрыты коллизиями имён (`BookRequest` — тело сразу трёх разных эндпоинтов), схеме верить нельзя (см. `docs/UI-INVENTORY.md` §3.2).
2. Переписать пути и DTO под конверт, как в #53.
3. Решить судьбу модификаторов и слотов: либо скрыть в UI до расширения контракта, либо слать без них — но тогда чек приложения разойдётся с чеком бэкенда, что хуже.
4. Экран статуса заказа — на `food/orders/my`; кнопку «Отменить» скрыть, пока эндпоинта нет.
5. Промокод — на `GET promotions/check`.

Часть вопросов уходит в `jack5505/mahalla` (§5 `docs/UI-INVENTORY.md`) — отсюда метка `blocked`. Эпик: #9.

## T5. Room: миграции вместо fallbackToDestructiveMigration (обновление стирает корзину)

*Метки: `ai-task`, `android`*

### Проблема

`data/db/di/DatabaseModule.kt:26` — `.fallbackToDestructiveMigration()`, при этом `MahallaDatabase.kt:26` уже `version = 3`, а `exportSchema = false`.

Значит **любое обновление приложения, меняющее схему, молча стирает базу**: черновик корзины (`cart_draft_items`), офлайн-кэш мест (`places`) и заказы. Пользователь ставит обновление из Play и теряет собранную корзину — без единого сообщения.

Схем в git нет вовсе, поэтому написать миграцию задним числом уже нельзя: структуру v1 и v2 придётся восстанавливать по истории коммитов. **Чем позже возьмёмся, тем дороже** — база выросла с v1 до v3 за три эпика.

Риск записан в `AGENTS.md` ещё с эпика 1 («`exportSchema = false` включить обратно до первого релиза») и с тех пор только рос. В инвентаризации #57 его нет — она смотрела на продуктовый скоуп, а не на данные.

### Что сделать

- `exportSchema = true` + `room.schemaLocation` в `app/build.gradle.kts`; сгенерированные JSON-схемы **закоммитить** — они и есть источник миграций.
- Восстановить схемы v1 и v2 по истории (`git log -p` на `MahallaDatabase.kt`, `PlaceEntity`, `CartDraftItemEntity`) и написать `MIGRATION_1_2`, `MIGRATION_2_3`.
- Убрать глобальный `fallbackToDestructiveMigration()`. Если данными какой-то таблицы реально не жалко (кэш мест — не жалко, он перезапрашивается), то явный сброс только этой таблицы внутри миграции честнее, чем сброс всей базы.
- Тесты миграций: `androidx.room:room-testing` + `MigrationTestHelper`.

### Готово, когда

Обновление с v1 и с v2 сохраняет черновик корзины; схемы v1/v2/v3 лежат в репозитории; тесты миграций зелёные.

## T6. Карта: подключить готовый MapCanvas вместо заглушки

*Метки: `ai-task`, `android`, `screen`*

### Проблема

`feature/map/ui/MapScreen.kt:94` рисует `MapCanvasPlaceholder` — список маркеров текстом. При этом настоящее полотно **уже написано и покрыто тестами**: `feature/map/canvas/YandexMapCanvas.kt:148` — `MapCanvas`, с MapKit, кластеризацией, слоем «моё местоположение», диффом маркеров и подбором камеры (эпик 4.2, 29 тестов).

То есть между «карта работает» и «карта заглушка» — подключение готового компонента. Это самая дешёвая из оставшихся видимых задач.

### Что сделать

- Заменить `MapCanvasPlaceholder` на `MapCanvas(initializer, markers, camera, …)`, отобразив домен в `MapMarkerUi` / `MapCameraPosition`.
- Подгружать места по видимой области: `GET places/map-bounds` при остановке камеры (debounce — иначе запрос на каждый кадр панорамирования).
- Решить судьбу сеточного `MarkerClusterer` из эпика 4: MapKit кластеризует сам через `ClusterizedPlacemarkCollection`, так что свой кластеризатор либо удалить, либо оставить только для экранов без карты. Мёртвый код с тестами создаёт ложное ощущение покрытия.
- Проверить лицензионную плашку Яндекса — требование условий использования MapKit.

### Блокер (действие пользователя)

Нужен секрет **`MAPKIT_API_KEY`** в Settings → Secrets and variables → Actions, и его проброс в env шага сборки в `ci.yml` / `claude*.yml`. **Workflow-файлы правит только пользователь** — у GitHub App агента нет прав на `.github/workflows`. Без ключа `MapKitInitializer` вернёт `MissingApiKey` и на месте карты останется объяснение (это работает и тестами закрыто, но карты не будет).

Слайс эпика #8.

### Готово, когда

На экране карты видны тайлы и кластеры, тап по маркеру открывает карточку места, `testDebugUnitTest` и `lintDebug` зелёные.

## T8. Отчёты о падениях: Crashlytics или Sentry

*Метки: `ai-task`, `android`*

### Проблема

В проекте **нет ничего для сбора падений** — `grep -i 'crashlytics\|sentry\|firebase'` по `libs.versions.toml` и `app/build.gradle.kts` пусто.

Сейчас краш у пользователя невидим полностью: эмулятора в CI нет, ни один экран приложения на устройстве не проверялся (это записано риском в каждом разделе `AGENTS.md`), и единственный канал обратной связи — скриншот в issue, как было с #49 и #54. Приложение с MapKit, Keystore, биометрией и кастомным TLS — то есть с кодом, который ведёт себя по-разному на разных прошивках, — до релиза без отчётов о падениях выпускать нельзя.

В инвентаризации #57 этого пункта нет: она разбирала эндпоинты бэкенда, а не эксплуатацию.

### Что сделать

- Выбрать: Firebase Crashlytics (бесплатно, тянет Google Play Services — в Узбекистане устройства без сервисов Google обычны, это уже учитывалось в эпике 4.2) или Sentry (self-hosted, без зависимости от Google). **Выбор — решение продукта, задачу начать с него.**
- Подключить только в release (и в debug — по флагу, чтобы не засорять).
- **Не логировать секреты**: токены сессии, PIN, тела ответов бэкенда (в них по #34 может быть чувствительное). Список редактируемых полей — тот же, что у `HttpLoggingInterceptor` и `ChuckerHttpInspector`.
- Ключ/DSN — через переменную окружения и секрет Actions, как `MAPKIT_API_KEY` (#8/4.2), **в репозиторий не класть**.
- Non-fatal отчёты в местах, где сейчас ошибка глотается: `runCatchingCancellable` в PIN/DataStore, `runCatchingMapKit`, отказ Keystore.

### Готово, когда

Падение в release-сборке доезжает до панели; в отчёте нет токенов; `assembleRelease` зелёный.

## T9. Карточка места: лайк, «Избранное», комментарии

*Метки: `ai-task`, `android`, `screen`*

### Проблема

Контроллер `social` бэкендом отдаётся целиком, приложением не используется вовсе. Карточка места сейчас — только чтение: посмотреть и уйти. Ни одного действия, которое возвращало бы человека в приложение.

### Что сделать

- `GET places/{id}/status` → `liked`, `saved`, `totalLikes` — состояние кнопок при открытии карточки.
- `POST places/{id}/like`, `POST places/{id}/save` — оптимистичное обновление с откатом при ошибке (иначе сердечко «залипает» на медленной сети).
- `GET/POST places/{id}/comments` — лента комментариев, отдельно от отзывов с оценкой.
- Раздел «Избранное» из `GET saved-places`.

### Важно про «Избранное»

`GET saved-places` отдаёт **только UUID'ы** (`PageResponseUUID`), без карточек мест. То есть экран избранного получается N+1 запросом: список id, потом `GET places/{id}` на каждый. Прежде чем писать, **завести вопрос в `jack5505/mahalla`** — вернуть с этого эндпоинта карточки. Если ответа не будет, реализовать через N+1 с ограничением параллельности и кэшем в Room, и записать это как долг.

### Готово, когда

Лайк и сохранение работают и переживают перезаход на экран; «Избранное» открывается; откат при ошибке покрыт тестом ViewModel.

## T10. Оставить отзыв: POST reviews (сейчас отзывы только читаются)

*Метки: `ai-task`, `android`, `screen`*

### Проблема

Приложение умеет только `GET` отзывов (`CatalogApi`, эпик 4). Оставить свой отзыв нельзя, хотя рейтинг — главный сигнал в выдаче и на карточке места. Каталог наполняется отзывами только со стороны, а пользователь приложения в этом не участвует.

### Что сделать

- `POST reviews` — оценка (1–5), текст, привязка к месту; `DELETE reviews/{id}` для своего отзыва.
- Фото к отзыву через `POST media/upload` (multipart, `entityType`/`entityId`) — зависит от задачи про Coil для показа.
- Условие показа формы: отзыв логично предлагать после заказа/визита. Пока вертикали не доведены, достаточно кнопки на карточке места.
- Своё и чужое различать: у своего отзыва — удаление, у чужого нет. Ответ заведения (`POST reviews/{id}/reply`) — бизнес-панель, сюда не входит.
- Локальное обновление рейтинга после отправки: пересчитывать самим не надо, перезапросить карточку.

### Осторожно с контрактом

Имена полей отзыва в схеме стенда наполовину угаданы (`userName`/`author`, `text`/`comment`) — springdoc перекрыл `Response` коллизией имён, см. #53 и `docs/UI-INVENTORY.md` §3.2. **Тело `POST reviews` снять curl'ом, а не по схеме.**

### Готово, когда

Отзыв отправляется и появляется в списке, своё удаляется, ошибка показывается текстом бэкенда (#34); тесты ViewModel зелёные.

## T11. Центр уведомлений: список, бейдж непрочитанного, переход по entityId

*Метки: `ai-task`, `android`, `screen`*

### Проблема

Контроллер `notification` бэкендом отдаётся, приложением не используется. Пользователь не узнаёт ни о статусе заказа, ни об акциях, ни о чём-либо ещё, пока сам не откроет нужный экран.

### Что сделать

- `GET notifications?page&size` — экран списка, прочитанные и непрочитанные визуально различимы.
- `GET notifications/unread-count` — бейдж на иконке в топбаре главной. Обновлять при возврате на экран (`ON_RESUME`), а не только при старте.
- `PUT notifications/read-all` — «прочитать всё»; отметка отдельного уведомления — если эндпоинт есть, снять curl'ом.
- Переход по `type` + `entityId` в нужный экран через уже существующие типизированные маршруты (`navigation/Routes.kt`). Незнакомый `type` не должен ронять экран — открывать список.

### Связь с другими задачами

Это **клиент-side половина** пуш-уведомлений. Вторая половина — FCM (эпик #15): `DeviceDescriptor.fcmToken` уже объявлен и всегда `null`, поле ждёт подключения FCM, а токен уже отправляется на бэкенд вместе с устройством в `send-otp`/`refresh`. Центр уведомлений имеет смысл и без пушей, поэтому делается отдельно и раньше.

### Готово, когда

Список читается, бейдж показывает непрочитанное и гаснет после «прочитать всё», переход по уведомлению открывает нужный экран; тесты ViewModel зелёные.

## T12. Экран обязательного обновления: app/version/check

*Метки: `ai-task`, `android`*

### Проблема

Бэкенд умеет `POST app/version/check` → `updateRequired`, `updateAvailable`, `policy`, `remainingSkips`, `storeUrl`, и `POST app/version/skip`. Приложение об этом не знает.

При этом контракт бэкенда за последний месяц ломался четыре раза (#42, #51, #53 и пути `food/*`), и каждый раз старая сборка на устройстве переставала работать молча — человек видел «Nimadir xato ketdi» и не понимал, что надо обновиться. Задача дешёвая и снимает целый класс будущих обращений.

### Что сделать

- Проверка версии один раз за запуск, под держащимся splash'ем — рядом с `BackendUrlStore.hydrate()` в `RootViewModel.resolveStart` (там уже собрана вся стартовая логика).
- `updateRequired` → **блокирующий** экран без кнопки «назад»: объяснение + кнопка в `storeUrl`.
- `updateAvailable` + `remainingSkips > 0` → мягкое предложение с «Позже», счётчик пропусков через `POST app/version/skip`.
- Отказ сети на этой проверке **не должен запирать приложение**: не ответил — пускаем дальше. Иначе упавший бэкенд превращается в кирпич на всех устройствах.
- `storeUrl` открывать через intent с проверкой схемы, как `TelegramBotLink.sanitize` в #46: адрес приходит с сервера, а адрес сервера в debug вводит пользователь.

### Готово, когда

При `updateRequired` приложение показывает блокирующий экран, при недоступном бэкенде — не показывает; тесты на все три исхода (required / available / сеть молчит) зелёные.

## T13. Размер APK: 123 МБ, из них 98 МБ — четыре копии libmaps-mobile.so (закрывает #28)

*Метки: `ai-task`, `android`*

### Замер

`./gradlew assembleDebug` на текущем `main` → **123 МБ**. Разбор содержимого:

| Что | Размер |
|---|---|
| `lib/x86/libmaps-mobile.so` | 27.7 МБ |
| `lib/x86_64/libmaps-mobile.so` | 27.4 МБ |
| `lib/arm64-v8a/libmaps-mobile.so` | 25.3 МБ |
| `lib/armeabi-v7a/libmaps-mobile.so` | 18.1 МБ |
| `classes*.dex` (без R8) | ~42 МБ в `classes.dex` + ещё 25 МБ в `classes18/19.dex` |

**98.5 МБ из 123 — это одна и та же нативная библиотека Yandex MapKit в четырёх архитектурах.** Из них `x86` и `x86_64` (55 МБ) нужны только эмулятору: телефонов на x86 практически нет.

Вторая половина — dex: `app/build.gradle.kts:92` в release стоит `isMinifyEnabled = false`, то есть R8 не работает вовсе, `proguardFiles` перечислены, но не применяются.

Это ответ на вопрос из #28 («изо чего»).

### Что сделать

1. **Публиковать App Bundle (`bundleRelease`), а не APK.** Google Play сам доставит устройству один ABI — пользователь скачает ~40 МБ вместо 123. Это главное решение, остальное — довесок.
2. Для APK-раздачи (стенд, тестировщики) — `splits { abi { … } }` или `ndk { abiFilters("arm64-v8a", "armeabi-v7a") }`: минус 55 МБ сразу.
3. **Включить `isMinifyEnabled = true` и `shrinkResources = true` в release.** Обязательно проверить правила ProGuard для: MapKit (нативные вызовы), Retrofit + kotlinx.serialization, Room, Hilt, Chucker no-op. После включения — прогнать `assembleRelease` **и** проверить приложение на устройстве: R8 ломается молча, в рантайме.
4. Проверить, не тянется ли MapKit `-full` где-нибудь транзитивно (в каталоге стоит `4.42.0-lite` — должно быть только оно).
5. Зафиксировать замер в CI, чтобы размер не уполз обратно.

### Готово, когда

`bundleRelease` собирается, скачиваемый размер на устройстве измерен и записан в issue, release с R8 работает на устройстве (не только собирается); `testDebugUnitTest`, `lintDebug`, `assembleRelease` зелёные.

Закрывает #28.
