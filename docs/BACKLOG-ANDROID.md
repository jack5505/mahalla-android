# Backlog Android — Mahalla

Разбор того, что осталось реализовать в `mahalla-android`, разложенный на эпики
и задачи, пригодные для создания issues. Составлен 2026-08-25 по issue #1.

## На чём стоим (снимок кода)

Готово:

- Gradle-каркас: wrapper 8.11.1, AGP 8.7.3, Kotlin 2.0.21, version catalog,
  модуль `app`, `namespace`/`applicationId = uz.mahalla`, minSdk 26 / targetSdk 35,
  portrait-only (`app/build.gradle.kts`, `app/src/main/AndroidManifest.xml`).
- Тема варианта B «Focus»: `Color.kt` (ColorScheme + семантические `MahallaColors`
  через `LocalMahallaColors`), `Type.kt`, `Shape.kt`, `Theme.kt` (+ `Spacing`),
  шрифт Inter (4 начертания) — `app/src/main/java/uz/mahalla/ui/theme/`.
- Юнит-тесты темы: `ThemeSelectionTest`, `ContrastTest`.
- CI: `ci.yml` (гейт на PR), `claude-dev.yml`, `claude.yml`.

Нет ничего из этого:

- ни одного экрана из 35 (в `MainActivity.kt` — заглушка);
- навигации, DI, сетевого слоя, хранилища, i18n-строк (в `values/strings.xml`
  только `app_name`);
- библиотеки UI-компонентов из `DESIGN-SYSTEM.md`;
- **проект ни разу не собирался** — это блокер #1.

Зависимости в `libs.versions.toml` минимальны: core-ktx, lifecycle, activity-compose,
Compose BOM, material3, junit. Всё остальное (navigation, hilt, retrofit, coil,
datastore, maps, robolectric, turbine, mockk) ещё предстоит добавить.

## Как читать backlog

- **Приоритет**: `P0` — блокирует всё остальное, `P1` — основной путь пользователя,
  `P2` — важно, но после основного пути, `P3` — можно позже.
- **DoD одинаковый для всех задач** (правило проекта, `AGENTS.md`): код + unit-тесты
  в том же коммите, `./gradlew testDebugUnitTest` и `./gradlew assembleDebug` зелёные,
  результат прогона — в описании PR. Instrumentation-тесты в CI не гоняем (эмулятора нет).
- Для каждого экрана считается выполненным только то, что сверено с прототипом
  (`design/android/prototype/`) в **обеих темах и обоих языках** (light/dark × ru/uz).

> ⚠️ Список экранов ниже восстановлен по `AGENTS.md` и общему описанию продукта:
> из CI нет доступа к репозиторию дизайна `jack5505/mahalla`, где лежит
> `design/android/TZ-ANDROID.md` §7 с точным перечнем 35 экранов. Первая задача
> эпика E0 — сверить этот backlog с ТЗ и поправить состав/названия экранов.

## E0 — Фундамент (P0)

Без этого эпика экраны писать бессмысленно: каждый следующий экран будет
переизобретать навигацию, состояния и компоненты.

### E0-1. Сверить backlog с ТЗ и SCREENS.md
Получить доступ к `jack5505/mahalla` из окружения агента (отдельный репозиторий
в GitHub App / `gh` в allowed-tools / submodule / копия `design/android/` в этот репо),
вычитать `TZ-ANDROID.md` §7 и `SCREENS.md`, привести список экранов и их названия
к ТЗ, дополнить критерии приёмки. Побочный результат: решить, как агент в CI будет
смотреть прототип.
**Приёмка**: `docs/BACKLOG-ANDROID.md` содержит ровно 35 экранов с именами из ТЗ;
расхождения зафиксированы.

### E0-2. Первая зелёная сборка и прогон тестов (BLOCKER)
Проект ни разу не собран. Прогнать `./gradlew assembleDebug` и
`./gradlew testDebugUnitTest`, починить всё, что вылезет (версии, лицензии SDK,
`local.properties`). В CI-workflow добавить агенту разрешения на `./gradlew`
(сейчас `claude.yml` не задаёт `--allowed-tools`, и агент не может собрать проект).
**Приёмка**: обе команды зелёные локально и в `ci.yml` на PR; вывод приложен.

### E0-3. Библиотека UI-компонентов по DESIGN-SYSTEM.md
`ui/components/`: кнопки (primary/secondary/ghost, 44 dp, minTouch 48 dp), текстовые
поля (46 dp, состояния normal/focused/error/disabled), чипы/фильтры (28 dp), карточки,
списковые строки, badges, bottom navigation (58 dp), top app bar, bottom sheet,
divider, rating, price/tnum-текст.
**Приёмка**: каждый компонент — с `@Preview` в light и dark; unit-тесты на чистую
логику (форматирование, выбор цвета по состоянию); визуальная сверка с прототипом.

### E0-4. Состояния экрана: loading / empty / error / skeleton
Единые `LoadingState`, `EmptyState`, `ErrorState` (+ retry), skeleton-заглушки списков,
единый способ показа snackbar.
**Приёмка**: компоненты используются всеми экранами следующих эпиков; unit-тесты на
маппинг ошибки → сообщение пользователя (uz/ru).

### E0-5. Навигация (Navigation Compose)
Single-activity, типизированный граф маршрутов, вложенные графы (onboarding, discovery,
vertical, profile, business), bottom nav с сохранением состояния табов, deep links
(заготовка), безопасная передача аргументов.
**Приёмка**: unit-тесты на построение/парсинг маршрутов и аргументов; переход между
всеми существующими заглушками экранов работает.

### E0-6. Архитектура пакетов + DI (Hilt)
Слои `core/` (ui, network, storage, common) и `feature/<name>/` (ui, data, domain),
Hilt, ViewModel + `StateFlow`-UI-state, `Result`-обёртка, корутин-диспетчеры через DI
(для тестируемости).
**Приёмка**: описан контракт слоёв в `docs/ARCHITECTURE.md`; unit-тест ViewModel'а
на подменённых зависимостях проходит.

### E0-7. Сетевой слой
Retrofit + OkHttp + kotlinx.serialization, base URL из BuildConfig (dev/prod),
интерсептор авторизации, refresh токена, таймауты, маппинг HTTP/сетевых ошибок в
доменные, логирование только в debug.
**Приёмка**: unit-тесты на MockWebServer (успех, 401 + refresh, 5xx, таймаут,
нет сети); секреты и URL не хардкодятся в код.

### E0-8. Локальное хранилище и безопасность
DataStore (язык, тема, онбординг пройден, последняя геопозиция), токены — в
EncryptedSharedPreferences/Keystore, PIN — только хеш, никогда в открытом виде.
**Приёмка**: unit-тесты репозитория настроек; тест, что токен не попадает в логи.

### E0-9. Локализация uz/ru + форматирование
Все строки — в `values/strings.xml` (uz) и `values-ru/strings.xml`, переключатель языка
в приложении (не только системный), форматирование сумм (UZS, tabular numerals `tnum`),
дат/времени, номеров телефонов `+998`, номеров талонов.
**Приёмка**: unit-тесты форматтеров (сумма, телефон, талон, дата) для uz и ru;
ни одной строки в коде; проверка обоих языков на прототипе.

## E1 — Онбординг и авторизация (P1)

Порядок из ТЗ: welcome → phone → otp → pin → biometric → geo.

### E1-1. Welcome
Приветственный экран, выбор языка (uz/ru) до логина, кнопка «Начать».
**Приёмка**: язык сохраняется в DataStore и применяется сразу; unit-тест ViewModel.

### E1-2. Ввод телефона
Маска `+998 (__) ___-__-__`, валидация оператора/длины, согласие с условиями,
запрос кода.
**Приёмка**: unit-тесты валидатора (валидные/невалидные номера, вставка, backspace).

### E1-3. OTP
6 ячеек, автофокус, вставка кода из SMS-буфера, таймер повторной отправки,
блокировка после N попыток, ошибки от бэкенда.
**Приёмка**: unit-тесты таймера/попыток/успеха; экран не даёт бесконечно долбить API.

### E1-4. Создание и ввод PIN
Установка PIN (двойной ввод), вход по PIN, лимит попыток, сброс.
**Приёмка**: unit-тесты логики сравнения хешей и блокировки; PIN не логируется.

### E1-5. Биометрия
BiometricPrompt поверх PIN, опциональность, корректное поведение при отсутствии
сенсора/отзыве разрешения.
**Приёмка**: unit-тесты состояния «доступна/недоступна/отключена пользователем»;
без биометрии вход по PIN не ломается.

### E1-6. Разрешение геолокации
Экран-объяснение до системного диалога, обработка «отказано» и «отказано навсегда»,
ручной выбор города/района как fallback.
**Приёмка**: unit-тесты редьюсера состояний разрешения; discovery работает без GPS.
